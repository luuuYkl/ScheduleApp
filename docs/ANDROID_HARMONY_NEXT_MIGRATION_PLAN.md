# ScheduleApp 转换到 Android 与鸿蒙 NEXT 的方案规划（无代码版）

## 1. 当前项目现状与迁移前提

- 当前前端为 **Vue 3 + TypeScript + Vite + Pinia + Vue Router**，属于标准 Web 单页应用，具备较高的跨端迁移基础。
- 业务能力完整：登录注册、计划/任务/日程、日志、AI 建议、主题切换，适合先“保功能”再“提体验”的迁移策略。
- 数据层当前支持 Mock 与真实后端切换，可作为移动端迁移阶段的“功能回归与联调开关”。

---

## 2. 目标与约束

### 2.1 迁移目标

1. 在不重写业务规则的前提下，尽快上线 Android 与鸿蒙 NEXT 可用版本。
2. 保留现有页面结构与核心交互，优先实现功能一致性。
3. 后续逐步增强为“接近原生体验”（通知、离线、性能、系统能力集成）。

### 2.2 迁移约束

- 当前前端大量依赖浏览器能力（localStorage、DOM、主题属性切换等），需要评估在容器内是否行为一致。
- AI 接口与 API 域名在移动端需要考虑网络安全策略、证书、白名单与隐私合规。

---

## 3. 总体技术路线（建议分两条并行）

## 路线 A：快速上线（Web 容器化）

### Android

- 使用 Web 容器方案（如 WebView 容器框架）直接承载现有 H5。
- 优点：上线快、改造少、前端团队可主导。
- 适用：MVP、快速验证留存与业务价值。

### 鸿蒙 NEXT

- 使用鸿蒙 NEXT 的 Web 承载能力（ArkUI + Web 组件）嵌入现有 Web 应用。
- 构建与 Android 类似的“容器壳 + H5 业务”形态，保持双端发布节奏一致。

### 路线 A 输出

- 双端可安装包
- 与 Web 端功能基本一致
- 基础登录、计划/任务/日程、日志、AI 能力可用

---

## 路线 B：中长期优化（逐步原生化）

- 逐步将“高频场景”做原生化界面与能力接入（如通知、系统日历、后台任务、深色主题跟随系统）。
- Web 业务逻辑保留，原生层通过桥接提供系统能力。
- 最终形态可为“混合架构”：
  - 高频核心页面：原生
  - 长尾配置/活动页：Web

---

## 4. 分阶段实施计划

## Phase 0：迁移准备（1~2 周）

1. **梳理功能清单与验收标准**
   - 按模块建立“Web 现状 -> 移动验收项”对照：认证、计划、任务、日志、AI、主题、路由守卫。
2. **端能力盘点**
   - 明确 Android 与鸿蒙 NEXT 下可用能力：网络、存储、推送、通知、分享、文件、生命周期。
3. **统一环境配置策略**
   - 区分 dev/test/prod 的 API 与 AI 配置，不在客户端硬编码敏感信息。

## Phase 1：容器化落地（2~4 周）

1. **Android 壳工程搭建**
   - 完成 Web 容器加载、启动页、网络权限与基础打包。
2. **鸿蒙 NEXT 壳工程搭建**
   - 完成 Stage 模型应用壳、Web 组件加载、路由入口与签名配置。
3. **桥接能力最小集**
   - 定义统一 JS-Bridge 能力清单：
     - 设备信息
     - 本地通知
     - 安全存储（替代明文 localStorage）
     - 应用版本查询
4. **功能回归测试**
   - 以现有页面为回归主线，保证关键路径可用。

## Phase 2：稳定性与体验优化（2~6 周）

1. **性能优化**
   - 首屏加载、页面切换、列表滚动与低端机适配。
2. **离线与弱网策略**
   - 增加缓存策略、失败重试、离线提示。
3. **安全与合规**
   - Token 安全存储、日志脱敏、隐私弹窗、用户协议与权限说明。
4. **崩溃与埋点体系**
   - 建立双端一致的埋点与异常上报模型。

## Phase 3：原生增强（按业务优先级持续）

1. 消息提醒与日程通知深度集成
2. 与系统日历/提醒事项联动
3. 原生组件替换高频交互页
4. 多终端一致性（Web、Android、鸿蒙）统一设计系统

---

## 5. 架构设计建议

## 5.1 业务分层（保持可演进）

- **展示层**：Web 页面（短期保留）/ 原生页面（长期替换）
- **领域层**：计划、任务、日程、日志、AI 的业务规则（尽量平台无关）
- **数据层**：API 访问、缓存、鉴权、错误处理
- **平台层**：Android/Harmony 特有能力（通知、存储、生命周期）

## 5.2 配置与环境治理

- 建立统一配置中心：
  - API Base URL
  - AI 服务开关与模型参数
  - Mock 开关仅在开发环境开放
- 生产环境禁止将 API Key 放在客户端包体。

## 5.3 数据与状态迁移策略

- 当前 localStorage 方案在移动端建议升级为“安全存储 + 业务缓存分离”：
  - token、用户敏感信息 -> 安全存储
  - 非敏感业务缓存 -> 常规本地存储

---

## 6. Android 重点方案

1. **版本策略**：先支持主流 Android 版本区间，减少兼容成本。
2. **网络安全**：配置 HTTPS 与证书策略，避免明文接口。
3. **生命周期**：处理前后台切换、WebView 进程回收后的状态恢复。
4. **通知能力**：对接本地通知与后续推送扩展。
5. **商店发布**：包名、签名、隐私协议、应用权限说明一次性规范。

---

## 7. 鸿蒙 NEXT 重点方案

1. **工程形态**：采用 Stage 模型规范化工程目录与多模块组织。
2. **Web 承载与桥接**：统一 JS-Bridge 协议，保持与 Android 桥接接口一致。
3. **分发要求**：遵循应用市场合规要求（隐私、权限、网络访问）。
4. **性能关注点**：针对 Web 容器渲染特性做首屏、列表与路由切换专项优化。

---

## 8. 测试与验收策略

## 8.1 测试分层

- **功能回归**：按现有业务流逐条验收。
- **兼容测试**：不同机型、系统版本、深浅色模式。
- **异常测试**：断网、弱网、接口超时、Token 过期。
- **发布测试**：安装升级、冷启动/热启动、后台恢复。

## 8.2 验收基线（建议）

- 核心路径成功率 ≥ 99%
- 冷启动可用时间在可接受阈值内
- 关键崩溃率达标
- AI 功能在“有 Key/无 Key（Mock）”两种模式下均可控

---

## 9. 风险清单与应对

1. **风险：容器性能不足**
   - 应对：先做性能基线，必要时将高频页面原生化。
2. **风险：端上存储安全不足**
   - 应对：敏感数据迁移到安全存储，不再依赖明文 localStorage。
3. **风险：AI 接口合规与费用不可控**
   - 应对：服务端代理与配额控制，客户端仅拿业务结果。
4. **风险：双端桥接接口分裂**
   - 应对：制定统一 Bridge 协议与版本控制策略。

---

## 10. 组织与排期建议

- **团队角色**：前端（H5）+ Android + 鸿蒙 + 后端 + 测试 + 产品。
- **里程碑建议**：
  - M1：双端壳工程跑通 + 首页可用
  - M2：核心功能全链路可用（登录、计划、任务、日志）
  - M3：性能/稳定性达标并提测
  - M4：首发上线 + 迭代原生增强

---

## 11. 推荐落地结论

- 短期采用“**容器化快速上线**”，确保业务尽快进入 Android 与鸿蒙 NEXT。
- 中期进入“**混合架构演进**”，把通知、离线、系统日历等高价值能力原生化。
- 长期实现统一设计系统与统一领域模型，降低三端长期维护成本。
